## 1. Результат среза

Игрок выбирает одну из трёх предложенных стран. Начинается небольшой одиночный матч: человек и три ИИ, четыре уникальные цивилизации. У каждого участника одна столица с одним жителем, центральной клеткой и шестью доступными соседями. За тестовую сессию игрок исследует мир, видит работу жителей, открывает технологии и культуру, строит здания, развивает территорию и основывает ещё один город.

Все участники готовят планы на одном снимке состояния. После фиксации всех планов общий resolver рассчитывает результат; визуальная часть показывает полученные движения и изменения. Завершается разрешение — начинается новое планирование.

Рекомендуемая проверочная сессия — 15–25 ходов, около 15–25 минут; это цель теста удобства, а не обязательное окончание партии. Срез не объявляет победу за количество городов/технологий, не останавливает игру на 48-м ходу и не показывает «эпоха закончилась». Цель полной игры в 1–2 часа остаётся в OpenSpec; проверить её на этом объёме контента нельзя.

## 2. Правила, которые сохраняем

- Небольшая гексагональная карта с горизонтальным замыканием. Север и юг не соединяются. Все игровые расстояния, обзор, соседи, территории, реки, поиск пути и размещение стартов используют одну топологию.
- Россия, США, Молдавское княжество и Римская империя не меняют идентичность при развитии. Человек получает три карточки выбора, ИИ — оставшиеся разные страны.
- Город начинается с одного жителя. Центральная клетка даёт базовый доход без работника. Остальные клетки не приносят доход сами.
- Каждый житель занимает только одну клетку или одно рабочее место здания. Рабочих юнитов нет.
- Автоматическое распределение жителей использует доступные рабочие места; модель хранит назначение, UI и анимации показывают это же назначение.
- Ресурсный бонус требует открытия, работника и улучшения. Назначенный свободный житель прокладывает тропу и создаёт примитивное улучшение в том же разрешении хода. Без свободного жителя освоение ждёт.
- Здания занимают отдельные клетки городской территории. Рабочий доход здания зависит от занятого рабочего места; пассивные эффекты явно отделены от него.
- Еда/население относятся к городу; наука/культура/золото — к державе. Научный и культурный прогресс независимы. Вклад города в культуру также используется для его территориального роста.
- Выборы доступны по правилам контента. При одновременной необходимости решений сначала наука, затем культура, затем производство городов, затем приказы юнитам.
- ИИ планирует по тем же правилам и использует тот же resolver. Планирование не начисляет доходов и не перемещает отряды.
- Камера имеет фиксированный изометрический угол; разрешены перемещение и масштаб. Год и номер хода отображаются, «лет за ход» не отображается.
- Рандом контролируется seed и сохраняемым состоянием. Ожидание игрока и частота кадров не меняют результат разрешения.

| Система | Сейчас | Переделка по OpenSpec |
| --- | --- | --- |
| Участники | Один безымянный игрок | Человек + три ИИ, уникальные страны и отдельные державы |

| Доход | Бонусы всех соседних ресурсов автоматически | Центр + фактически занятые клетки/рабочие места |
| Жители | Декоративный цикл вокруг костра | Задания модели, путь до рабочего места, соответствующая профессия |
| Ресурсы | Видны и дают бонус без освоения | Ворота открытий, назначение работника, тропа, улучшение |
| Здания | Список названий и бонусов, модели на центральной клетке | Объекты с отдельной позицией, пассивными эффектами и рабочими местами |
| Развитие | Только исследование; содержание зашито в C# | Независимые наука и культура; описания контента в данных |
| План | Изменяемые маршруты; отсутствие приказа молча считается ожиданием | Проверяемые данные плана, явный приказ ожидания, фиксация готовности |
| Разрешение | Unity-корутина по очереди меняет модель шагами | Общий resolver всех участников; корутина только проигрывает результаты |
| Движение | Нет проверки претендентов и занятых клеток | Общие микрошаги, конкуренция за клетку, скорость и контролируемая случайность |
| Интерфейс | Две постоянные боковые панели и большая верхняя полоса | Тонкая общая полоса, мини-карта, панель города/отряда, центральные карточки и правая кнопка шагов |
| Календарь | Только ход | Общий год и ход; экономика не умножается на календарный интервал |
| Завершение | 48 ходов или 2 города / 6 открытий / 10 жителей | Нет искусственного финала ранней эпохи |

Можно переиспользовать подготовку Unity-проекта, Windows-сборку, часть процедурной геометрии, палитру и инструменты проверки. Генератор, модель экономики, приказов и жизнедеятельности требуют изменений. Старую формулу доходов нельзя сохранять под новым интерфейсом.

## 4. Предлагаемое содержимое

Это выбор для первого среза из чернового контента OpenSpec, а не утверждение окончательного дерева.

| Категория | Предложенный объём |
| --- | --- |
| Карта | Настраиваемый небольшой размер; стартовый профиль около 32 × 20 гексов, проверяемый для четырёх стартов |
| Местность | Луг, равнина, лес, холмы, горы, побережье, океан; остальные биомы следующим расширением |
| Ресурсы | Камень, зерно, рыба, дичь и меха; бонусы закрыты соответствующими открытиями |
| Технологии | Огонь, обработка камня, охота и следопытство, рыболовство, земледелие, гончарное дело |
| Культура | Устные предания, наскальная живопись, игла; родовые связи и сезонные праздники — при готовности минимальной модели счастья |
| Здания | Общий очаг, каменная мастерская, рыбацкая хижина, гончарная мастерская, амбар; длинный дом — вместе с родовыми связями |
| Улучшения | Тропа, каменоломня, поле на зерне, рыбацкая стоянка, охотничья/меховая стоянка |
| Отряды | Разведчик, базовый воин, поселенцы; боевые параметры в мирном срезе не используются |
| Профессии | Работа на обычной клетке, земледелец, каменотёс, рыбак, охотник/обработчик шкур, ремесленник |
| События | Два проверяемых ранних события, например удачная охота и разлив реки; вероятность, условия и эффекты в данных |

Городское здание через очередь и автоматическое улучшение ресурса — разные объекты. Например, поле на открытом зерне строит назначенный житель; оно не должно одновременно появляться второй бесплатной копией здания из очереди.

Карточку не включаем в случайный пул, пока её обещанный эффект не реализован. Это особенно важно для дипломатических, религиозных и боевых открытий. Когда оставшихся доступных карточек меньше трёх, предлагаем все оставшиеся; это явно указанная обработка конца ограниченного пула, а не добавление фиктивных вариантов.

## 6. Открытые решения и пробные настройки

Ниже — предложения для первого теста, которые необходимо обозначать как экспериментальный профиль баланса. Они не редактируют исходный OpenSpec.

1. **Базовая экономика.** Вынести доходы центра, клеток и зданий, потребление, запас пищи, пороги роста и стоимости в `DemoBalance`. Начать с ориентиров §10: около трёх ходов на открытие/заказ и около пяти на первый рост. Примерные 3 науки, 3 культуры, цена 9, производство 5 и цена 15 не обязаны получиться именно такими после назначения одного жителя. Сначала проверяем суммы источников дохода.
2. **Автоназначение.** Предлагается сначала избегать дефицита пищи, затем сравнивать доступные рабочие места по настраиваемым весам; равенство разрешать стабильным ID. Не добавлять произвольный доход «за население». Переназначение при новом открытии/постройке и статус «свободного жителя» должны иметь явные правила; не списывать рабочего дважды.
3. **Строительная клетка.** Для первых тестов предлагается автоматический выбор свободной пригодной клетки внутри города, с показом места в карточке. Рабочее место, место стройки и занятая местность не должны одновременно начислять три дохода одному жителю.
4. **Культурные границы.** Предлагается накопление городского культурного влияния до настраиваемого порога и присоединение одной доступной соседней клетки. Чужую территорию не перезаписывать; конкуренция и очередь разрешаются детерминированно. Точный порог и ранжирование — TBD.
5. **Семантика карточек развития.** §11.1 описывает выбор «при готовом открытии», в то время как старый прототип сначала назначает исследование, затем копит прогресс. Предлагаем для среза общий запас науки/культуры: при достижении цены появляется выбор, выбранное открытие оплачивается из запаса и вступает в силу по явному порядку разрешения. Момент выдачи первых карточек и альтернативный вариант выбора цели заранее нужно уточнить до этого этапа; нельзя переносить старую механику незаметно.
6. **Инициатива.** Формула `скорость × 3 + d6` в OpenSpec не утверждена. Нужен тестовый вариант, где быстрый обычно выигрывает, равные скорости равноправны, медленный сохраняет небольшой шанс. Все броски — из сохраняемого RNG, независимо от порядка обхода участников; точный вариант отдельно фиксируется в профиле.
7. **Занятые клетки.** Для мирного теста предлагается одна наземная группа на клетке, явное ожидание, обработка дружеских обменов/циклов одновременного освобождения и остановка при заблокированном входе. Это временные правила для проверяемого разрешения, не утверждённая боевая система.
8. **Основание города.** Стоимость, стартовые отряды, расход населения на поселенца и расстояние между городами — TBD. Старые значения «минус один житель» и «минимум четыре клетки» не считаются требованиями OpenSpec; их можно использовать только как явно обозначенные пробные настройки.
9. **Календарь.** Дата старта и шкала — отдельные данные тестового профиля. Все державы получают один год; смена шкалы не меняет доход за ход. Не привязывать конец ограниченного контента к принудительному историческому финалу.
10. **Счастье и хранение еды.** Карточки с такими эффектами подключать после минимальной реализации и ясного обозначения влияния. Вместимость, запас роста, переполнение и бонус амбара нужно разделить; нельзя незаметно заменить ёмкость постоянной прибавкой еды, как в старом прототипе.

## 7. Порядок реализации и проверка каждого шага

### Шаг 1. Модель города и экономики

Отделить определения контента от состояния. Ввести державу-владельца, территорию города, жителей, рабочие места и улучшения. Исправить начальное население и модель дохода. Временные числа хранятся в отдельном тестовом профиле, а не как свойства окончательного дизайна.

Проверка: центр работает без жителя; пустой луг не даёт доход; один житель не занимает два места; закрытый/неосвоенный ресурс не даёт бонус; при свободном работнике открытый ресурс получает тропу и улучшение в тот же ход; население не растёт от ожидания между ходами.

Промежуточная сцена одного города допустима для проверки этого шага, но не называется готовой одиночной демкой.

### Шаг 2. Мир, шов и четыре старта

Ввести общую цилиндрическую топологию и периодическую генерацию ландшафта. Разместить четыре стартовые области, проверить доступность еды/производства и разумные расстояния. Отдельный туман для участников. Игровые русла и визуальные плавные линии рек должны согласованно переходить через шов; камера и визуальные копии у краёв показывают движение непрерывно.

Проверка: переходы соседей через оба края, кратчайший маршрут через шов, обзор/территория/река через шов, отсутствие северо-южного замыкания, воспроизводимость зерна и пригодность всех четырёх стартов.

### Шаг 3. Состояние матча и разрешение приказов

Ввести `MatchState`, `FactionState`, `TurnPlan`, явные приказы `Move`, `Wait`, `FoundCity`, `SetProduction` и решения развития. Фиксированный план нельзя менять. Resolver обрабатывает общие микрошаги движения на снимке, разрешает претендентов, рассчитывает экономику, завершения, рост, границы и отчёт событий. Визуальные корутины не меняют исход решения.

Проверка: чужой приказ отклоняется; планирование не начисляет доход; один ход нельзя разрешить дважды; общий снимок устраняет зависимость от порядка участников; конфликт не создаёт наложение юнитов; одинаковые состояние/планы/RNG дают одинаковый результат.

### Шаг 4. Наука, культура и производство

Подключить ограниченный каталог из §4, отдельные державные запасы и зависимости. Добавить рабочие места построек, автоматическое освоение разрешённых ресурсов, строительство на отдельных клетках, культурное расширение. Выборы сохраняются при закрытии окна; из пула исключаются недоступные и уже завершённые одноразовые объекты.

Проверка: нет карточек с незапущенными эффектами; наука не расходует культуру; культура города учитывается и державой, и его влиянием; зданию нужен работник только для явно рабочего дохода; закрытый ресурс не осваивается; цена и описание карточки совпадают с расчётом.

### Шаг 5. Выбор стран и ИИ

Три карточки выбора человеку, уникальное назначение четырёх стран. AI planner строит планы во время планирования человека и использует один публичный набор правил. Контролируемый RNG для решений, а не зависимость от длительности думающего кадра. При недостатке разных цивилизаций выдаётся ошибка старта.

Проверка: в матче четыре разных владельца/страны; у ИИ такие же жители и доходы; ИИ не движется до resolver; продолжение после загрузки даёт одинаковый результат; игрок не управляет чужими объектами.

### Шаг 6. Живой город и интерфейс

Профессии и пути жителей берутся из экономического назначения. Показать движение к реальному месту работы, рабочее действие и отдых. Фиксировать угол камеры. Добавить тонкую строку державных ресурсов и даты, мини-карту, панели города/отряда, центральные карточки и крупную правую кнопку следующего нерешённого шага.

Кнопка: события → наука → культура → города → юниты → завершить ход. Для отряда без движения игрок подтверждает ожидание; это не потерянный приказ. Видно число нерешённых городов и отрядов. События появляются в отчёте следующего планирования с причиной и последствиями.

Проверка: пропускаемые шаги действительно пропускаются; карта не закрыта постоянными карточками; игрок видит, где работает единственный житель, почему ресурс закрыт и какое решение мешает завершить ход; профессия меняется вместе с назначением.

### Шаг 7. Сохранение и непрерывное развитие

Один локальный слот в фазе планирования: версия данных, карта, владельцы/исследование, города, жители/рабочие места, улучшения, здания, отряды, приказы, державные ресурсы/открытия, календарь, RNG и уже выданные карточки. Первая демонстрация развития — появление тропы/улучшения и соответствующее обновление доступного объекта; следующий визуальный материал подключается отдельным контентным расширением, без экрана смены эпохи.

Проверка: состояние до сохранения и после загрузки совпадает; продолжение при тех же приказах воспроизводимо; повторная загрузка не перебрасывает карточки; конец текущего каталога не завершает эпоху автоматически.

### Шаг 8. Сборка и приёмочный прогон

Windows-сборка, проверка карты/шва/городов визуально, ручной полный проход интерфейса и автоматические проверки модели. Отдельно измерить первые десять ходов: науку, культуру, заказы, рост, свободную рабочую силу и очереди. После измерений корректировать пробный профиль, не переписывать OpenSpec.

Срез готов, когда можно выбрать страну, сыграть 15–25 ходов с тремя действующими ИИ, освоить ресурс через настоящего жителя, построить здание на клетке, получить открытия науки и культуры, перейти отрядом через горизонтальный шов, основать город, увидеть отчёт события, сохранить/загрузить и продолжить без принудительного конца эпохи.

## 8. Предлагаемая архитектура

| Слой | Ответственность |
| --- | --- |
| Content | Определения цивилизаций, клеток, ресурсов, открытий, зданий, отрядов, событий; зависимости, эффекты, визуальные ключи |
| Balance | Версионированный экспериментальный профиль: цены, доходы, рост, инициатива, календарь, размеры карты |
| State | Сериализуемое состояние матча, держав, городов, жителей, назначений, карты, отрядов, предложений и RNG |
| Planning | Проверка и фиксация приказов; AI planner; отсутствие изменений экономического состояния |
| Simulation | Городская экономика, автоназначение, освоение, общий turn resolver, события и детерминированный результат |
| Presentation | Unity-сцена, модели, камера, анимация результатов, интерфейс; без собственной формулы дохода |
| Persistence | Версия формата, локальный слот, контроль совместимости каталога и состояния случайности |
| Verification | Инварианты рабочих мест, экономика, wrap, конфликты, воспроизводимость, сохранения и приёмочный сценарий |

Каталог можно хранить в JSON или ScriptableObject и преобразовывать в чистые определения; игровой Core не должен зависеть от Unity-объектов. Вид хранения выбирается при первом техническом шаге. Рандом генератора, карточек, ИИ и разрешения должен иметь отдельные явно сохраняемые потоки либо фиксированную схему потребления, чтобы изменение анимации не меняло исход партии.
